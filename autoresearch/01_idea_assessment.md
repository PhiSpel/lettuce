# Autoresearch Question Design — Critical Assessment

**Subject:** "Implement a non-reflecting boundary condition (NRBC) for LBM in `lettuce`, including the validation cases, as a reusable autoresearch/eval task."

**Assessor's scope:** grounded in a full read of `lettuce/` (~6 000 LOC), `tests/` (~2 500 LOC), `examples/`, `pyproject.toml`, `uv.lock` and `.github/workflows/CI.yml` at commit `121359d`.

**Caveat up front:** no PyTorch is installed in the environment this assessment was written in (`python3 -c "import torch"` → `ModuleNotFoundError`, `nvidia-smi` reports no driver). Every runtime figure and every baseline reflection coefficient below is a **reasoned estimate, not a measurement**. §8 lists exactly what must be measured before publishing.

---

## 1. Verdict

**Yes — with modifications. Three of them are load-bearing.**

The NRBC idea is a genuinely good fit for this codebase: the physics is real, the metric is a scalar, the reference solution can be generated by the harness itself, and — crucially — **the repo has no existing acceptance test that measures outlet reflection at all**, so the task is not already solved anywhere in the tree. But the idea as stated ("implement an NRBC and its benchmark") has three defects that would make it a weak benchmark:

**Defect 1 — the agent writes both the ruler and the thing being measured.** If the agent builds the validation case *and* the BC, the task has a built-in conflict of interest and the score is not comparable across agents. Two agents will build two different reflection metrics and their numbers will be incomparable. *Fix:* split into two tasks, or fix the benchmark spec and grade the BC with a harness the agent never sees.

**Defect 2 — "implement an NRBC" is nearly free to fake.** [`AntiBounceBackOutlet`](../lettuce/ext/_boundary/anti_bounce_back_outlet.py#L13) and [`EquilibriumOutletP`](../lettuce/ext/_boundary/equilibrium_outlet_p.py#L12) already hand the agent the entire index/slice/mask boilerplate (the `self.index` / `self.neighbor` construction at [anti_bounce_back_outlet.py:46-69](../lettuce/ext/_boundary/anti_bounce_back_outlet.py#L46) is copy-pasteable verbatim). An agent can produce a plausible-looking, running, subclass in twenty minutes. *Fix:* grade **only** on a quantitative reflection coefficient measured against the existing outlets as baselines. "It runs" must be worth zero points.

**Defect 3 — the stated "HPC / machine operations" axis is not exercised at all.** On the CPU path this task is pure `torch.roll` + `einsum`. The `cuda_native` subsystem ([`lettuce/cuda_native/`](../lettuce/cuda_native/_generator.py#L18), ~1 000 LOC of string templating that runs `setup.py install` at runtime, [_generator.py:111-127](../lettuce/cuda_native/_generator.py#L111)) is entirely bypassed. *Fix:* be honest that this task tests **physics + numerics + scientific measurement discipline**, and put the HPC axis in a separate task (§7, candidate C3).

With those fixed, the task is good. §9 recommends a tiered design; §10 argues that a **drag-coefficient task (C6)** and a **skipped-test bugfix (C5)** are cheaper and at least as discriminating, and would make a better *first* publication.

## 2. What the code actually looks like (grounding)

### 2.1 The `Boundary` contract

Five abstract methods, [`_flow.py:31-52`](../lettuce/_flow.py#L31):

```
__call__(flow) -> torch.Tensor          # must return a FULL [q, *resolution] field
make_no_collision_mask(shape, context)  # -> bool tensor or None
make_no_streaming_mask(shape, context)  # -> bool tensor or None
native_available() -> bool
native_generator(index) -> NativeBoundary
```

This is genuinely small. An agent can read it in one screen. Four concrete implementations exist ([`_boundary/__init__.py:1-13`](../lettuce/ext/_boundary/__init__.py#L1)), ranging from 32 lines ([`BounceBackBoundary`](../lettuce/ext/_boundary/bounce_back_boundary.py#L10)) to 109.

### 2.2 How boundaries hook in — and the traps

* **Boundaries run only inside `_collide()`**, [`_simulation.py:258-305`](../lettuce/_simulation.py#L258). Pre-boundaries fire before the collision operator, post-boundaries after; **both are pre-streaming**. There is no post-streaming hook. A scheme that needs to touch `f` between streaming and collision cannot be expressed as a `Boundary`.
* **Streaming is `torch.roll`**, [`_simulation.py:242-256`](../lettuce/_simulation.py#L242). **The domain is periodic in every direction by default.** Any outlet must set `make_no_streaming_mask` correctly or the wrap-around silently survives. This is the single most likely first-attempt bug and a good discriminator.
* **`no_collision_mask` is an integer ownership field, not a boolean**, [`_simulation.py:104-107`](../lettuce/_simulation.py#L104), dtype `uint8`. Each node is assigned the *index* of the single component that owns it; later boundaries overwrite earlier ones ([lines 120](../lettuce/_simulation.py#L120), [142](../lettuce/_simulation.py#L142)). **Consequence: a node can belong to exactly one boundary, and a node owned by a boundary does not get the normal collision.** This matters enormously for NRBCs: a *sponge / absorbing layer* spanning 20–50 cells would claim all of them and thereby disable BGK inside the sponge. The correct pattern is to reimplement collision inside the boundary, exactly as [`PartiallySaturatedBC`](../lettuce/ext/_boundary/partially_saturated_boundary.py#L22) does (it blends bounce-back with its own BGK step at [lines 26-37](../lettuce/ext/_boundary/partially_saturated_boundary.py#L26)). An agent that does not notice this will produce a sponge that is also a no-collision slab — which *will* still damp, and *will* still score, and will be physically wrong. A good grader must catch this (see §4.4 anti-gaming guard 4).
* **Two contradicting `__call__` contracts.** `torch.where(eq(mask, i), boundary(flow), flow.f, out=flow.f)` at [`_simulation.py:291-304`](../lettuce/_simulation.py#L291) implies the boundary returns a whole-domain tensor. `BounceBackBoundary` and `PartiallySaturatedBC` obey this. But [`AntiBounceBackOutlet.__call__`](../lettuce/ext/_boundary/anti_bounce_back_outlet.py#L81) *mutates `flow.f` in place* and returns it, making the `torch.where` a no-op self-copy. `EquilibriumOutletP` does the same ([equilibrium_outlet_p.py:70-73](../lettuce/ext/_boundary/equilibrium_outlet_p.py#L70)). An agent copying the outlet will inherit the in-place idiom; an agent copying `BounceBackBoundary` will not. Both work. This is an honest "the codebase is not as simple as it looks" data point.
* **`post_boundaries` is a `@property` that constructs new objects on every access** — see [`Obstacle.post_boundaries`](../lettuce/ext/_flows/obstacle.py#L108). `Simulation.__init__` reads it **twice**: once for `self.transformer` ([_simulation.py:70](../lettuce/_simulation.py#L70)) and once for `self.post_boundaries` ([line 73](../lettuce/_simulation.py#L73)). The two lists contain *different instances*. **Any stateful boundary is a trap here.** This matters directly: a convective/Orlanski outlet must remember `f` or `u` from the previous step. It will work (because only `self.post_boundaries` is called in `_collide`), but the agent must realise state must be initialised lazily in `__call__`, not in `__init__` against a `flow` that might be re-instantiated. A nice, non-obvious, *discoverable* difficulty.
* **Deprecation smell**: three parallel names `boundaries` / `pre_boundaries` / `post_boundaries`, with a `warnings.warn` fired from inside a property ([`_flow.py:103-114`](../lettuce/_flow.py#L103)). `Obstacle` defines `post_boundaries`; the test harness's `TestFlow` defines `boundaries` ([conftest.py:226](../tests/conftest.py#L226)); the skipped outlet test overrides `boundaries` ([test_equilibrium_pressure_outlet.py:19](../tests/boundary/test_equilibrium_pressure_outlet.py#L19)) and is therefore *already partly broken* against the current `Simulation`.

### 2.3 The two existing outlets are already weakly non-reflecting

This is the most important thing to understand before pricing the task.

* [`AntiBounceBackOutlet`](../lettuce/ext/_boundary/anti_bounce_back_outlet.py#L71): **linear extrapolation** of the wall velocity, `u_w = u[b] + 0.5*(u[b] - u[b-1])` ([lines 78-80](../lettuce/ext/_boundary/anti_bounce_back_outlet.py#L78)), then anti-bounce-back of the outgoing populations with the local `rho`. This is Krüger §5.3.5. It is a *pressure* outlet and it is **already partially non-reflecting for hydrodynamic modes** but reflects acoustics.
* [`EquilibriumOutletP`](../lettuce/ext/_boundary/equilibrium_outlet_p.py#L63): **zeroth-order extrapolation** of `u` from the neighbour plane ([line 69](../lettuce/ext/_boundary/equilibrium_outlet_p.py#L69)) with a *fixed* `rho_outlet` ([line 68](../lettuce/ext/_boundary/equilibrium_outlet_p.py#L68)), overwriting the whole plane with `f^eq`. Imposing a hard `rho` is exactly the thing that makes an outlet acoustically reflective. Expect this one to be the *worse* baseline.

So the agent is not starting from "a wall". It is starting from two decent-but-reflective outlets and must beat them measurably. **That is the right shape for a benchmark** — it rules out trivial wins and gives the grader a meaningful denominator.

### 2.4 What is measurable out of the box — and what is missing

Observables in [`observable_reporter.py:12-14`](../lettuce/ext/_reporter/observable_reporter.py#L12): `MaximumVelocity`, `IncompressibleKineticEnergy`, `Enstrophy`, `EnergySpectrum`, `Mass`. Plus [`ErrorReporter`](../lettuce/ext/_reporter/error_reporter.py#L9) (L2 error vs. an analytic solution) and [`NaNReporter` / `HighMaReporter`](../lettuce/ext/_reporter/failure_reporter.py#L10).

**There is no point-probe / time-series-at-a-location reporter.** Every acoustic reflection metric needs one. The grader must supply it (~15 lines subclassing `Reporter`). This is fine — it keeps the harness self-contained — but it means the *task statement cannot say "use the existing reporters"*.

Also note `Enstrophy` is documented as periodic-domains-only ([lines 47-51](../lettuce/ext/_reporter/observable_reporter.py#L47)) and `Mass` hard-codes a `[..., 1:-1, 1:-1]` 2D slice ([line 155](../lettuce/ext/_reporter/observable_reporter.py#L155)) — it is **wrong in 1D and 3D**. Do not build a grader on `Mass`.

### 2.5 How correctness is currently asserted — the crucial gap

The boundary tests are **algorithmic-identity tests, not physics tests**. [`test_antibounceback_outlet_bc.py`](../tests/boundary/test_antibounceback_outlet_bc.py#L6) re-derives the Krüger formula by hand and compares tensors. [`test_equilibrium_bc_outlet_p.py:99-100`](../tests/boundary/test_equilibrium_bc_outlet_p.py#L99) asserts `rel=1e-2` with an inline `# TODO rel is too big!`. And [`test_equilibrium_pressure_outlet.py:5`](../tests/boundary/test_equilibrium_pressure_outlet.py#L5) is **`pytest.skip("TODO rtol is too big or simulation time too short!")`** — the one test that actually tried to assert an outlet's *physical* behaviour is disabled.

**Nobody in this repo has ever measured how reflective these outlets are.** That is what makes the proposed task real research rather than a re-implementation exercise — and it is also the strongest argument for publishing it.

## 3. Feasibility

### 3.1 Which NRBC family, and how hard is each *here*

| Family | Core idea | Fit to this architecture | Verdict |
|---|---|---|---|
| **Convective / Orlanski outflow** | ∂φ/∂t + U_c ∂φ/∂n = 0, discretised on `f` or on `(ρ,u)` | Needs one stored previous-step plane. Expressible as a `Boundary`; must dodge the property-reinstantiation trap (§2.2). | **Best T1 target.** ~60–100 LOC. Well documented in the literature (Yang 2013; Lou et al. 2013). |
| **Absorbing / sponge layer** (target-state damping, viscosity ramp) | Blend `f` toward a target `f^eq(ρ∞,u∞)` over a ramped zone | Architecturally awkward: a multi-cell zone claims `no_collision_mask` for all its cells ([§2.2](#22-how-boundaries-hook-in--and-the-traps)), so the boundary must re-run collision itself. `PartiallySaturatedBC` is the precedent. | **Good T1/T2 target.** Easy physics, *non-obvious* integration — exactly the difficulty profile you want. |
| **Characteristic BC / LODI** (Izquierdo–Fueyo 2008; Heubes et al. 2014) | Decompose into acoustic/entropy/vorticity characteristics, suppress the incoming one, reconstruct ρ,u then `f^eq + f^neq` | Doable: `initialize_f_neq` at [`_flow.py:341-366`](../lettuce/_flow.py#L341) shows the reconstruction pattern. Corners in 2D are genuinely hard. | **T2/T3.** This is where competent agents separate from good ones. |
| **PML** (Najafi-Yazdi & Mongeau 2012) | Auxiliary variables + modified streaming | **Out of scope.** Requires modifying the streaming step, which `Boundary` cannot reach ([§2.2](#22-how-boundaries-hook-in--and-the-traps)). Would need a `Simulation` fork. | **Exclude** — and say so in the task statement, or agents will burn hours on it. |
| **Zou–He** | Prescribed velocity/pressure via non-equilibrium bounce-back | **Not an NRBC.** It is a Dirichlet BC and is *strongly* reflective. Mentioning it in the task statement would be a red herring. | Exclude from this task; see C1 in §7 — it is a fine *separate* task. |

### 3.2 Can a competent agent do it in a bounded session?

**Yes, for tiers 0–2. Probably not for tier 3 without real iteration budget.**

Working in its favour: 5-method interface; two copy-able outlets; pure Python/torch, no compile step on the CPU path; a 1D D1Q3 case runs in seconds so the agent gets a fast feedback loop; and the literature is well-known to a pretrained model.

Working against it: the periodic-`torch.roll` trap; the `no_collision_mask` ownership semantics; unit conversions (lu ↔ pu, [`_unit.py`](../lettuce/_unit.py#L13)) where a missing `c_s²` changes an answer by 3× **without crashing**; and the fact that building a *correct reference solution* (a long domain whose far end never contaminates the probe window) requires the agent to reason about wave travel times rather than just run something.

There is also a real footgun: **`Context()` with no arguments auto-selects CUDA *and* `use_native=True`** ([`_context.py:17-20`](../lettuce/_context.py#L17)), and neither existing outlet has a native generator ([anti_bounce_back_outlet.py:105](../lettuce/ext/_boundary/anti_bounce_back_outlet.py#L105), [equilibrium_outlet_p.py:87](../lettuce/ext/_boundary/equilibrium_outlet_p.py#L87)). On a GPU box the agent's first run will try to JIT-compile a CUDA extension. The task statement **must** pin `Context(device='cpu', use_native=False, dtype=torch.float64)`.

### 3.3 Is it trivially solved by copying an existing BC?

**Copying gets you the scaffolding, not the score** — *provided* the grader is a reflection coefficient. Copying `EquilibriumOutletP` and changing `rho_outlet` to the local extrapolated `rho` is a ~5-line change that already improves reflection somewhat; that is the floor. Copying alone cannot get to R ≤ 0.05, which requires either a real characteristic treatment or a tuned sponge. Set the tier-2 threshold there and the task is not copy-solvable.

### 3.4 Is it unbounded?

**Only tier 3.** "Build a Pareto front over NRBC families" is genuinely open-ended and should be time-boxed and rubric-graded, not pass/fail graded. Tiers 0–2 are bounded because the metric, the case, and the threshold are all fixed.

## 4. Measurability

This is where the design lives or dies. The good news: **acoustic reflection is a scalar with a self-generating reference.**

### 4.1 Primary case — 1D acoustic pulse (the cheap, robust core)

Why 1D: `D1Q3` exists ([`ext/_stencil/d1q3.py`](../lettuce/ext/_stencil/d1q3.py)), `ExtFlow` accepts `d=1` ([_ext_flow.py:22-26](../lettuce/ext/_flows/_ext_flow.py#L22)), and the stencil fixtures already exercise it ([conftest.py:18-19](../tests/conftest.py#L18)). Runtime is negligible. **Trap to document:** `initialize_f_neq` hard-codes two velocity components ([`_flow.py:348-354`](../lettuce/_flow.py#L348)) and will crash in 1D — the case must use `initialize_fneq=False`.

Concrete spec:

* Domain `N = 2000` lu, `D1Q3`, `float64`, CPU, `use_native=False`, `BGKCollision` with `tau = 0.6` (ν = 0.0333 lu, low enough that viscous decay over the window is small and *identical* between test and reference).
* Initial condition: `ρ = 1 + A·exp(−(x−x₀)²/(2σ²))`, `A = 1e-3` (linear acoustics — keeps the pulse out of the nonlinear regime so reflection is a clean linear coefficient), `σ = 10 lu`, `x₀ = 400`, `u = U₀` uniform.
* Mean-flow sweep `U₀ ∈ {0, 0.05·c_s, 0.10·c_s}`. Zero mean flow is the easy case; **non-zero mean flow is what breaks naive sponges and naive characteristic BCs**, because the acoustic and entropy modes then travel at different speeds.
* Outlet at `x = N−1` uses the candidate BC. Inlet at `x = 0` uses the *same* BC (symmetric), or the pulse is placed so it never reaches `x = 0` within the window — prefer the latter, it isolates one boundary.
* Probe at `x_p = 1000`, i.e. between the source and the outlet, so the outgoing pulse passes it on the way out and any reflection passes back through the *same* probe. The incident arrival is at `t ≈ (1000−400)/c_s ≈ 1 040` steps; the earliest reflection arrival is `t₁ = ((N−1−x₀) + (N−1−x_p))/c_s ≈ (1 599 + 999)·√3 ≈ 4 500` steps.
* Window `T = 5 500` steps (comfortably past `t₁`, well before viscous decay matters at `tau = 0.6`).
* **Reference run**: identical, but `N_ref = 6 000`. Its own outlet cannot contaminate `x_p` before `t ≈ (5 600 + 5 000)·√3 ≈ 18 000 ≫ T`. Generated by the grader at grade time — **no stored reference data, no data drift.**

### 4.2 The metric

Let `p'(t) = ρ(x_p, t) − 1`.

**Primary (robust, recommended):**

```
R_L2 = ‖p'_test(x_p, ·) − p'_ref(x_p, ·)‖₂  /  ‖p'_ref(x_p, ·)‖₂        over t ∈ [0, T]
```

This is better than a peak-ratio because it penalises **both** under-absorption (a reflected pulse) **and** over-absorption / distortion (a BC that also eats the outgoing wave, or that drifts the mean density). It is a single number, it is monotone in "how good is the BC", and it cannot be gamed by moving energy around in time.

**Secondary (interpretable, report alongside):**

```
R_peak = max_{t ∈ [t₁,T]} |p'_test|  /  max_{t ∈ [0,t₁]} |p'_test|
```
with `t₁ ≈ 4 500` as derived above (minus a `3σ/c_s` margin so the incident tail is excluded). This is the number a reviewer recognises as "the reflection coefficient".

**Expected values** (order-of-magnitude, from the LBM NRBC literature; **must be measured before publishing**, §8):
`EquilibriumOutletP` ≈ 0.2–0.5 · `AntiBounceBackOutlet` ≈ 0.05–0.2 · well-tuned sponge ≈ 0.01–0.03 · good characteristic BC ≈ 0.005–0.02.

**Thresholds** (state as a ratio to the measured baseline so they survive re-measurement):
* T1 pass: `R_L2 ≤ 0.5 × min(baseline_ABB, baseline_EQP)` at `U₀ = 0` **and** `U₀ = 0.05 c_s`.
* T2 pass: `R_L2 ≤ 0.05` absolute, across the whole `U₀` sweep **and** in 2D (§4.3).
* T3: report the frontier; no fixed threshold.

### 4.3 Discriminating case — 2D, oblique incidence and corners

1D alone is too easy and rewards the wrong thing (a 1D sponge is nearly trivial). The case that actually separates methods:

* `D2Q9`, `256 × 256`, cylindrical Gaussian density pulse at the centre, `A = 1e-3`, `σ = 8`, `u = U₀ x̂`.
* **All four faces** use the candidate BC, including the four corners. Corners are where most textbook NRBCs quietly fail, because the characteristic decomposition is direction-specific and the corner node has two owners — and recall from [§2.2](#22-how-boundaries-hook-in--and-the-traps) that `no_collision_mask` gives a corner to **exactly one** boundary, whichever is listed last. An agent that does not handle this will get a visible corner artefact that `R_L2` will catch.
* Reference: `768 × 768` with the pulse in the centre, sampled on the inner `256 × 256`.
* Metric: `R_L2 = ‖p'_test − p'_ref‖_F / ‖p'_ref at t=0‖_F`, evaluated on the inner `128 × 128` at `t = 1.4 × (128/c_s)` (after the pulse has fully left the test domain but before the reference pulse reaches *its* boundary).

### 4.4 Anti-gaming

A reflection metric is far harder to game than a "does it run" test, but not impossible. Four guards, all cheap:

1. **Incident-wave fidelity.** Assert `|peak_incident_test − peak_incident_ref| / peak_ref < 0.02`. Kills "damp everything": a BC whose sponge reaches upstream of the probe will fail this even while scoring a low `R_L2` in isolation.
2. **Through-flow conservation.** At `U₀ = 0.05 c_s`, assert the mean outlet mass flux matches the reference within 1 %. Kills "freeze the field near the boundary", which is otherwise a perfect absorber and a useless BC.
3. **Held-out configurations.** Publish one worked config; **grade on different `N`, `σ`, `A`, `U₀`, and on the 2D case**. The grader instantiates the agent's `Boundary` subclass itself against a flow the agent never saw. This is the single most important guard — it kills hard-coded damping profiles, tuned-to-the-test-case constants, and memorised answers.
4. **No-collision-slab check.** Assert that the candidate's `make_no_collision_mask` claims at most `k` cells per face (`k = 1` for a local BC; declare an explicit budget, e.g. `k ≤ 40`, for a sponge) **and** that total kinetic energy in the interior at `t=0` is unchanged — catching a BC that accidentally disables collision over a third of the domain.
5. **Interface conformance.** The deliverable must be importable as a `lettuce.ext.Boundary` subclass and usable via `flow.post_boundaries`. No monkey-patching `Simulation`, no editing `_simulation.py`. Enforce by running the grader against a *clean* checkout of `lettuce/` plus only the agent's new file(s) — a `git diff --stat` allowlist.

### 4.5 Is the grader human-free?

**Yes for T0–T2.** It is one `grade.py` that: (a) imports the agent's module, (b) builds the reference by simulation, (c) runs the sweep, (d) emits JSON `{R_L2, R_peak, guards, pass/fail}`. No stored reference data, no plots to eyeball, no judgement calls.

**No for T3.** A Pareto-front / ablation task needs a rubric. That is acceptable — label it explicitly as rubric-graded and pre-register the rubric.

## 5. Replicability

**Good, and better than most scientific-computing repos — but only on the CPU path.**

* **Environment is already pinned.** `requires-python = "==3.12.*"` ([pyproject.toml:9](../pyproject.toml#L9)), a 284 KB `uv.lock`, and a `cpu` extra ([pyproject.toml:39-41](../pyproject.toml#L39)) pointing at the PyTorch CPU index. `uv sync --extra cpu && uv run pytest tests` is exactly what CI does ([CI.yml:40-45](../.github/workflows/CI.yml#L40)). A CPU-only variant is not just possible, it is the *default* CI configuration and one of six matrix entries ([CI.yml:23-29](../.github/workflows/CI.yml#L23)).
* **Pin the context explicitly in the harness:** `Context(device=torch.device('cpu'), dtype=torch.float64, use_native=False)`. Rationale in [§3.2](#32-can-a-competent-agent-do-it-in-a-bounded-session). `float64` is not optional — at `A = 1e-3` and `float32`, round-off is ~1e-7 relative, which is 1e-4 of the signal; measuring `R = 0.005` in `float32` is measuring noise.
* **Determinism.** No RNG in the core loop. The only randomness is `DecayingTurbulence`, which takes an explicit `randseed` ([decayingturbulence.py:31,90](../lettuce/ext/_flows/decayingturbulence.py#L31)) — avoid that flow anyway. Reduction order in `torch.einsum` / `torch.sum` can vary with thread count, so: set `torch.set_num_threads(1)`, and compare with `atol=1e-9` rather than bitwise. Expect run-to-run agreement to ~1e-12 in float64 single-threaded.
* **Explicitly exclude the native path.** `use_native=True` triggers runtime CUDA codegen + `subprocess([sys.executable, 'setup.py', 'install'])` into site-packages ([_generator.py:111-127](../lettuce/cuda_native/_generator.py#L111)). Non-hermetic, requires `nvcc`, mutates the environment, and — because `AntiBounceBackOutlet.native_generator` returns `None` ([line 108](../lettuce/ext/_boundary/anti_bounce_back_outlet.py#L108)) — probably does not even work for outlet flows. Off-limits for a benchmark.
* **Runtime (ESTIMATE — unmeasured).** `_stream` does `q−1` `torch.roll` calls per step ([_simulation.py:246-255](../lettuce/_simulation.py#L246)) plus a few `einsum`s. Single-threaded CPU float64: roughly 5–15 MLUPS.
  * 1D `N=2000`, 3 600 steps × 3 mean-flow values × (test + reference at `N=6000`): ~3·10⁷ node-updates → **seconds**.
  * 2D `256²`, ~1 000 steps: 6.6·10⁷ → **~10 s**. Reference `768²`: ~6·10⁸ → **~1–2 min**.
  * **Full grader: comfortably under 10 minutes on one CPU core.** That is an excellent property — it means the benchmark can run in GitHub Actions on the free tier, and it means the *agent* gets a fast inner loop.
* **What is not pinned:** BLAS/OpenMP thread count, and PyTorch minor version (`torch>=2.7.0` for the cpu extra is a floor, though `uv.lock` pins the resolution). Ship the lockfile and a `--frozen` sync in the harness.

## 6. The two claims, assessed honestly

### CLAIM 1 — "lettuce is suitable because of its simplicity"

**Mostly true, and the exceptions are features.**

Supporting: ~6 000 LOC in `lettuce/` (of which 645 are generated `_version.py`); `Simulation` is 343 lines total; `Boundary` is a 5-method ABC; `BGKCollision` is [11 lines of body](../lettuce/ext/_collision/bgk_collision.py#L17); `QuadraticEquilibrium` is [14 lines](../lettuce/ext/_equilibrium/quadratic_equilibrium.py#L46); `D2Q9` is [3 lines of data](../lettuce/ext/_stencil/d2q9.py#L72). No mesh generation, no MPI, no build step on the CPU path, no config-file DSL. [`examples/00_simplest_TGV.py`](../examples/00_simplest_TGV.py) really is 21 lines. An agent can hold the whole mental model.

Where it is **not** simple, and you should say so in the published task:
* The `no_collision_mask` integer-ownership semantics ([§2.2](#22-how-boundaries-hook-in--and-the-traps)) are documented only in inline comments in `_simulation.py`, not in any API doc, and they impose a real modelling constraint.
* Three overlapping boundary-list names with a live deprecation warning ([`_flow.py:103-120`](../lettuce/_flow.py#L103)); inconsistent adoption across `Obstacle` (uses `post_boundaries`) vs. the test harness (uses `boundaries`).
* Two contradicting `Boundary.__call__` conventions (return-a-field vs. mutate-in-place).
* `post_boundaries` as an object-constructing property called multiple times.
* `cuda_native/` (~1 000 LOC of templated C++/CUDA string generation with a runtime installer) is genuinely complex and is *not* covered by the simplicity claim.
* Half-supported 1D: `initialize_f_neq` is 2D/3D-only ([`_flow.py:348`](../lettuce/_flow.py#L348)), `Mass` observable is 2D-only ([observable_reporter.py:155](../lettuce/ext/_reporter/observable_reporter.py#L155)), `Enstrophy` is 2D/3D-only.
* The lu/pu unit system ([`_unit.py`](../lettuce/_unit.py#L13)) is a permanent source of silent factor errors — which is precisely why it is *good* benchmark material.

**Net:** simple enough that the task is tractable, rough enough that it is not trivial. That is the ideal operating point for an eval. Do not oversell it as "simple"; sell it as **"small enough to read in an afternoon, with real load-bearing conventions you must discover."**

### CLAIM 2 — "CFD is an interesting autoresearch domain"

**True, but for narrower reasons than stated, and with one contamination risk you must manage.**

What CFD tests that a web-app task does not:
1. **There is no oracle.** You cannot unit-test "is this physically correct". Establishing ground truth — a grid-convergence study, a long-domain reference, an analytic solution — *is the work*. In my experience of agent behaviour, this is the single most reliable discriminator: weak agents declare victory at "it runs and the plot looks smooth."
2. **Failures are silent and quantitative.** A missing `c_s²` does not raise; it changes the answer by a factor of 3. A wrong `no_streaming_mask` does not raise; the domain stays periodic and the "outlet" silently does nothing. Web-app tasks fail loudly.
3. **Stability is an independent axis from correctness.** A scheme can be consistent and unconditionally unstable. `tau → 0.5` is a real cliff. Nothing in CRUD-app benchmarks has this shape.
4. **Dimensional reasoning.** lu ↔ pu conversion is a genuine, checkable competence.
5. **The metric design is part of the research.** Choosing `σ`, the probe location, the window, and the reference domain size requires reasoning about physics, not just about code.

Where the claim overreaches, honestly:
* **"couples … machine/HPC operations" — not in this task.** The NRBC task never leaves single-device PyTorch. If you want that axis, it is a different task (C3 below).
* **Contamination is a live risk.** Izquierdo–Fueyo characteristic BCs, Orlanski outflow, and LBM sponge layers are all in the public literature in closed form, and `lettuce` itself is on GitHub. A strong model may reproduce a known formula from memory. **This is not fatal** — the benchmark measures whether the agent can *land* a method in an unfamiliar architecture and *prove* it works — but it does mean you must grade on the held-out metric, never on "did it pick the sophisticated method".
* **It is a narrow-population benchmark.** The number of people who can review a submission is small. Budget for that.

## 7. Alternative and complementary questions on this codebase

Difficulty is agent-hours for a competent model. Scores are 1–5 (5 = best).

### C1 — Zou–He (non-equilibrium bounce-back) velocity & pressure BC
No Zou–He exists in the repo (grep for it returns nothing). Implement for D2Q9 and D3Q19 with correct corner handling.
*Grader:* [`PoiseuilleFlow2D`](../lettuce/ext/_flows/poiseuille.py#L18) has an **analytic solution** ([lines 30-40](../lettuce/ext/_flows/poiseuille.py#L30)). Drive it with a Zou–He pressure drop instead of a body force; assert the L2 velocity error vs. analytic falls with observed order ≥ 1.9 over four resolutions {16,32,64,128}, and that mass is conserved to 1e-12.
**Difficulty: medium-low (2–4 h). Feasible 5 / Measurable 5 / Replicable 5.** The cleanest task in the set — an exact analytic reference makes grading unarguable.

### C2 — New stencil or new collision operator
e.g. a recursive-regularized (RR) collision, or an entropic ELBM step. `BGK/TRT/MRT/KBC/Regularized/Smagorinsky` already exist ([`_collision/`](../lettuce/ext/_collision/)), so the new one must be genuinely distinct. Note `D3Q27CumulantTransform` is a commented-out stub in [`util/moments.py:363`](../lettuce/util/moments.py#L363) — an obvious hole.
*Grader:* existing stencil invariants ([`tests/stencil/test_weights.py`](../tests/stencil/test_weights.py), `test_opposite.py`, `test_symmetry.py`) + moment-isotropy to the claimed order + 2D Taylor–Green L2 error vs. the [analytic solution](../lettuce/ext/_flows/taylorgreen.py#L66) showing 2nd-order convergence.
**Difficulty: medium (4–6 h). F 5 / M 5 / R 5.**

### C3 — Native CUDA codegen for a boundary that lacks one
`AntiBounceBackOutlet` and `EquilibriumOutletP` both return `native_available() -> False`. Write their `NativeBoundary` generators against [`cuda_native/ext/_boundary/equilibrium_pu.py`](../lettuce/cuda_native/ext/_boundary/equilibrium_pu.py) as the worked example.
*Grader:* native vs. torch agreement to 1e-10 in float64 over 100 steps on a fixed flow, plus a MLUPS speedup floor.
**Difficulty: high (6–10 h). F 3 / M 5 / R 2.** This is the *only* candidate that tests the HPC axis — and its replicability is poor (needs a GPU + `nvcc`, and the build writes into site-packages). Publish it as an optional GPU-tier companion, never as the core benchmark.

### C4 — Reproduce a published benchmark curve
The repo already ships **30+ digitised reference CSVs** for the 3D cylinder at Re=3900 from Lourenço–Shih 1993, Kravchenko–Moin 2000, Wissink–Rodi 2008, Dong et al. 2018 ([`examples/advanced_projects/efficient_bounce_back_obstacle/profile_reference_data/`](../examples/advanced_projects/efficient_bounce_back_obstacle/profile_reference_data/)). Task: set up the case and reproduce the `u_x` profiles at positions 1–3.
*Grader:* RMS deviation from the CSVs below a threshold, per position.
**Difficulty: high (8+ h, plus hours of compute). F 3 / M 5 / R 3.** The most authentically "research" task available here, and the reference data problem is already solved. Cost is the blocker: 3D, needs a GPU, multi-hour runs.

### C5 — Regression / bugfix: un-skip the pressure-outlet test ⭐
[`tests/boundary/test_equilibrium_pressure_outlet.py:5`](../tests/boundary/test_equilibrium_pressure_outlet.py#L5) — `pytest.skip("TODO rtol is too big or simulation time too short!")` — and [`test_equilibrium_bc_outlet_p.py:100`](../tests/boundary/test_equilibrium_bc_outlet_p.py#L100) — `rel=1e-2  # TODO rel is too big!`. Task: determine whether this is a tolerance problem, a too-short run, or a **real bug in `EquilibriumOutletP`**; fix it; un-skip at a tightened tolerance. (Note the skipped test also overrides the deprecated `boundaries` property rather than `post_boundaries`, so it is at least partly stale relative to [`_simulation.py:70-73`](../lettuce/_simulation.py#L70) — the agent must untangle that too.)
*Grader:* the test passes at a tightened tolerance on held-out `(stencil, dtype)` configurations, and the full suite still passes.
**Difficulty: medium (3–5 h). F 5 / M 5 / R 5.** This is the best SWE-bench-shaped item in the repo: a genuine open TODO left by the maintainers, with a crisp pass condition and near-zero setup cost. **Strongly recommend publishing this one first** — it is cheap to validate and it proves out the harness before you invest in the NRBC task.

### C6 — Drag/lift observable via momentum exchange ⭐
No force observable exists ([`observable_reporter.py:12-14`](../lettuce/ext/_reporter/observable_reporter.py#L12) lists only velocity/energy/enstrophy/spectrum/mass). Implement momentum-exchange force integration over a [`BounceBackBoundary`](../lettuce/ext/_boundary/bounce_back_boundary.py#L10) mask, expose it as an `Observable`.
*Grader:* 2D cylinder. Re=20 → C_d = 2.05 ± 5 %; Re=40 → C_d = 1.55 ± 5 %; Re=100 → Strouhal 0.164 ± 5 %. These are canonical, uncontested numbers.
**Difficulty: medium (4–6 h). F 5 / M 5 / R 4.** Arguably a **better flagship than the NRBC task**: the reference values are famous and unarguable, the metric is a plain scalar, no reference simulation is needed, and it forces the agent to get the `no_collision_mask` / bounce-back geometry exactly right — the same architectural competence the NRBC task probes, with none of the metric-design ambiguity.

### C7 — Numerical-stability frontier
Implement a collision operator (RR, entropic, or a cascaded/central-moment scheme) that extends the stable operating envelope.
*Grader:* the largest Mach number at which a `128²` [`DoublyPeriodicShear2D`](../lettuce/ext/_flows/doublyshear.py#L19) survives 10⁵ steps without NaN (use [`NaNReporter`](../lettuce/ext/_reporter/failure_reporter.py#L10) + `BreakableSimulation`), **subject to** enstrophy staying within 5 % of a fine-grid reference. The constraint is what stops the agent from "winning" with a maximally dissipative scheme.
**Difficulty: medium-high (5–8 h). F 4 / M 5 / R 4.** Metric is a scalar frontier and is very hard to game once the accuracy constraint is attached. Runtime is the main cost.

### C8 — Shan–Chen multiphase
*Grader:* Laplace law — Δp vs. 1/R linear with the theoretically predicted slope over four droplet radii; coexistence densities vs. the Maxwell construction.
**Difficulty: high (8+ h). F 3 / M 5 / R 4.** Grading is airtight and essentially un-gameable (you cannot fake a linear Laplace law). But it is a large new subsystem, not a boundary condition.

### C9 — Multi-GPU domain decomposition
Split `_stream` across devices with halo exchange.
**Difficulty: high. F 3 / M 4 / R 1.** Needs ≥2 GPUs. Good HPC axis, unusable as a shared benchmark.

### ✗ C10 — Immersed / interpolated bounce-back. **Do not use.** HWBB and linear-interpolated IBB were merged in commit `121359d` and live in [`examples/advanced_projects/efficient_bounce_back_obstacle/boundary/`](../examples/advanced_projects/efficient_bounce_back_obstacle/boundary/). The answer is in the repo. Contaminated by construction.

## 8. Must-measure-before-publishing checklist

None of the following could be measured here (no PyTorch in this environment). All are cheap.

1. **Baseline reflection coefficients.** Run the §4.1 case with `AntiBounceBackOutlet` and `EquilibriumOutletP`. Publish both `R_L2` and `R_peak`. **If the gap between the two baselines is smaller than the noise floor, the metric is not discriminating and the whole design needs revisiting.** This is the single highest-priority check.
2. **Confirm the 1D path works at all.** `D1Q3` + `ExtFlow(d=1)` + `AntiBounceBackOutlet(direction=[1], ...)`. Note `initialize_f_neq` will crash in 1D ([`_flow.py:348`](../lettuce/_flow.py#L348)) — confirm `initialize_fneq=False` is sufficient. If 1D turns out to be broken, fall back to a quasi-1D 2D strip (`N × 4`, periodic in y), which costs nothing extra.
3. **Wall-clock the full grader** on one CPU core. Target < 10 min. Adjust `N`, `N_ref` and the 2D resolutions to hit it.
4. **Determinism**: same run, 1 vs. 8 threads, float64 — record the actual spread and set the grader tolerance from it.
5. **Sanity-check the corner behaviour** of the 2D four-face configuration with the *existing* outlets, so you know what the baseline corner artefact looks like before you ask anyone to beat it.
6. **Verify the `git diff` allowlist** (§4.4 guard 5) actually blocks a `_simulation.py` edit.

## 9. Recommended tiered design for the NRBC task

Split the deliverable in two so the ruler and the object are never authored by the same agent.

**Task N-A — "Build the reflection benchmark."** Given: a written spec of the acoustic-pulse case and the metric (essentially §4.1–4.2, minus the numbers). Deliverable: a `Flow` subclass, a probe `Reporter`, and a `measure_reflection(boundary_factory) -> float` harness. *Graded* by running it against four BCs whose true `R` the maintainers measured beforehand (the two existing outlets, a deliberately bad one — e.g. full bounce-back — and a known-good reference sponge): the agent's harness must **rank all four correctly** and land within 20 % of the reference `R` values. This is a clean, fully automatic grader for a *measurement* skill, which is rarely benchmarked and is exactly the skill the "no oracle" argument in §6 is about.

**Task N-B — "Implement the NRBC."** Given: the maintainers' harness (as a black box the agent may call but not modify). Tiers:

* **T0 — smoke (~45 min).** Implement a convective (Orlanski) outlet as a `Boundary` for one axis-aligned face. *Pass:* correct interface, runs on `Obstacle`, no NaN over 2 000 steps, `AntiBounceBackOutlet`-style algorithmic test passes. Worth reporting but not scoring.
* **T1 — core (2–4 h).** `R_L2 ≤ 0.5 × min(baseline)` at `U₀ ∈ {0, 0.05 c_s}` in 1D, all four anti-gaming guards satisfied, on held-out `(N, σ, A)`.
* **T2 — hard (4–8 h).** 2D, all four faces incl. corners, `R_L2 ≤ 0.05` across the `U₀` sweep; plus the Lamb–Oseen vortex exit test — advect the existing [`LambOseenVortex2D`](../lettuce/ext/_flows/lamboseenvortex.py#L19) through the outlet and bound the residual pressure disturbance. **Include this vortex test:** it probes *hydrodynamic* (vorticity/entropy) mode transmission, which is a genuinely different failure mode from acoustics — sponges usually pass it, pure characteristic BCs often do not. A benchmark with only one failure mode is a benchmark you can overfit.
* **T3 — open (time-boxed).** Implement ≥ 2 distinct NRBC families, produce a Pareto front of `R_L2` vs. MLUPS penalty, with an ablation over sponge thickness / relaxation profile. Graded by a **pre-registered rubric** plus "does the submitted front dominate the reference front". Explicitly rubric-graded, explicitly not pass/fail.

**Fixed for every tier:** `Context(device='cpu', dtype=torch.float64, use_native=False)`, `torch.set_num_threads(1)`, `uv sync --frozen --extra cpu`, PML declared out of scope, no edits outside the agent's own new files.

## 10. Summary recommendation

1. **Publish C5 (un-skip the pressure-outlet test) first.** Two hours of maintainer time, it validates your whole harness, and it is a real open TODO the maintainers left behind. It is the cheapest possible proof that the pipeline works.
2. **Publish C6 (drag/lift via momentum exchange) as the flagship.** Canonical uncontested reference numbers, no reference simulation needed, and it exercises the same architectural competence (`no_collision_mask`, bounce-back geometry, `Observable` interface) as the NRBC task with none of the metric-design ambiguity.
3. **Publish the NRBC task as the hard tier**, split into N-A (build the ruler) and N-B (build the BC), with the modifications in §1. It is the most *interesting* of the three and the one that best supports the "CFD has no oracle" argument — but it is also the one where a sloppy design would produce incomparable numbers.
4. **Soften the two claims in the write-up.** "Simple" → "small enough to read in an afternoon, with real load-bearing conventions you must discover" (and list them — §6). Drop "HPC operations" from the NRBC framing entirely, or attach C3 as an explicit optional GPU tier.
5. **Do the §8 measurements before committing to any threshold.** Especially item 1: if the two existing outlets score the same, the metric is not discriminating and the design must change.
